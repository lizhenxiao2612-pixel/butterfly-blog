写代码时，最常见的失败方式是：把半个文件贴进去，说「修一下」。模型看不见项目约定，就会另起炉灶。把它当成坐在旁边的同事：先讲现场，再请它动手。

![一起在屏幕上揪出那只小 bug](/img/illust-code.png)

## 修 bug 时带上这四样

1. **现象**：实际发生了什么，期望是什么。
2. **复现**：最短步骤，最好能复制。
3. **现场**：相关函数或报错栈，而不是整个仓库。
4. **边界**：哪些文件不能动、风格要跟哪段现有代码。

```text
Python 3.12，函数 `parse_tags(raw: str) -> list[str]`。
输入 `"hexo, ai"` 时我希望得到 ["hexo", "ai"]，
现在空格还留在结果里。
请只改这一函数，补一个最小单测。
不要引入新依赖。
```

## 让它解释，而不是先改

面对看不懂的报错，先要解释路径，再允许改代码：

```text
先不要改代码。
用我能读懂的话说明：错误在哪一层发生、为什么会触发。
如果有两种可能原因，先列出来，问我要哪条路。
```

这能避免「看起来能跑、其实换了一种坏法」的补丁。

## 适合交给 AI 的，和不适合的

**适合：** 写样例、补测试、翻译报错、对照文档、把重复样板收成函数。

**你自己把关：** 鉴权、支付、删除数据、任何「错一次就不可逆」的逻辑。可以让它起草，但合并前必须你读过。
